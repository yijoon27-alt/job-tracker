# Job Tracker

공개 GitHub Pages에서 Google 계정으로 로그인하는 사용자별 비공개 공채 대시보드입니다. 사이트 코드는 공개되지만, 지원 기록은 Supabase 사용자 ID별로 분리되고 데이터베이스의 RLS 정책이 다른 사용자의 접근을 차단합니다.

## 1. Supabase 데이터베이스 설정

1. [Supabase](https://supabase.com/dashboard)에서 프로젝트를 만듭니다.
2. **SQL Editor**에서 [`supabase-schema.sql`](./supabase-schema.sql) 전체를 한 번 실행합니다.
3. 같은 SQL Editor에서 아래 문장만 따로 실행합니다. 이메일은 기존 기록을 가져갈 본인의 Google 이메일로 바꿉니다.

이미 운영 중인 프로젝트에 새 버전을 반영할 때도 `supabase-schema.sql` 전체를 다시 실행합니다. 스크립트는 기존 지원 기록을 삭제하지 않고 `서류 작성 여부`, `서류 마감 시각`, `AI 역량검사/인적성 마감과 결과` 같은 새 필드와 권한만 안전하게 추가합니다.

**2026-09-18 업데이트는 SQL 실행이 반드시 먼저입니다.** 특이사항·비고를 저장하는 `notes` 컬럼이 추가되어, 웹 파일만 올리면 목록 로딩과 저장이 실패합니다. 기존 기록은 지워지지 않고 빈 메모만 붙습니다.

**2026-09-16 업데이트도 SQL 실행이 반드시 먼저입니다.** 역량검사 유형을 저장하는 `assessment_type` 컬럼이 추가되어, 웹 파일만 올리면 목록 로딩과 저장이 실패합니다. 이 경우 앱이 `최신 DB 업데이트가 필요합니다` 안내를 표시합니다.

```sql
insert into private.legacy_migration_owners (email)
values (lower('YOUR_GOOGLE_EMAIL@gmail.com'))
on conflict (email) do nothing;
```

실제 이메일을 `supabase-schema.sql`이나 GitHub 파일에 적지 마세요. 위 설정은 공개 API에서 읽을 수 없는 `private` 스키마에 저장되며, 기존 기록 이전에만 사용됩니다.

## 2. Google 로그인 연결

1. [Google Auth Platform](https://console.cloud.google.com/auth/overview)에서 프로젝트와 OAuth 동의 화면을 설정합니다.
2. 데이터 접근 범위는 `openid`, 이메일, 기본 프로필만 사용합니다. Gmail·Drive 등의 추가 권한은 요청하지 않습니다.
3. **Web application** 유형의 OAuth Client를 만듭니다.
4. Authorized JavaScript origins에는 `https://yijoon27-alt.github.io`를 넣습니다. 경로 `/job-tracker/`는 origin에 넣지 않습니다.
5. Authorized redirect URIs에는 Supabase Dashboard의 **Authentication > Sign In / Providers > Google**에 표시되는 Callback URL을 정확히 넣습니다. 보통 다음 형태입니다.

```text
https://PROJECT_REF.supabase.co/auth/v1/callback
```

6. Google에서 발급된 Client ID와 Client Secret은 Supabase의 Google Provider 설정에만 입력하고 Google Provider를 활성화합니다.
7. Supabase의 **Authentication > URL Configuration**에서 Site URL과 Redirect URLs에 `https://yijoon27-alt.github.io/job-tracker/`를 등록합니다.
8. 이메일·비밀번호 로그인을 쓰지 않을 예정이면 Supabase에서 Email 로그인을 비활성화하고 Google Provider만 운영합니다.

**Google Client Secret은 GitHub, `config.js`, HTML, JavaScript, 채팅 또는 브라우저에 절대로 넣지 마세요.**

## 3. 웹 앱 연결

1. Supabase의 **Connect** 또는 **Settings > API Keys**에서 다음 두 값을 확인합니다.
   - Project URL: `https://...supabase.co`
   - Publishable key: `sb_publishable_...`
2. [`config.js`](./config.js)의 자리표시자를 위 두 값으로 교체합니다.
3. 변경 파일을 GitHub에 올리고 GitHub Pages 배포가 끝나면 Google로 로그인합니다.

`config.js`는 공개되는 파일입니다. Publishable key는 공개 웹 클라이언트용이지만 반드시 RLS와 함께 사용해야 합니다. 앱은 `sb_publishable_...` 형식이 아닌 키, 특히 `sb_secret_...` Secret key 사용을 실행 전에 차단합니다.

## 현재 현황판 및 전형 처리 규칙

### 전형 흐름

- 기본 흐름은 `서류 → 1차 면접 → 2차 면접 → 최종`입니다.
- 인적성 전형이 있는 공고는 `서류 → AI/인적성 → 1차 면접 → 2차 면접 → 최종`로 표시합니다. 등록·수정 패널에서 `AI 역검`이나 `인적성` 중 어느 쪽인지 고르면 현황판이 그 이름으로 바뀝니다. 고르지 않으면 지금처럼 `AI/인적성`으로 함께 적습니다. 전형이 있다는 표시는 마감일과 무관합니다. **마감일을 몰라도 결과를 `결과 대기`·`합격`·`탈락` 중 하나로 고르면 그 순간 인적성 전형이 생깁니다.** 해당 전형이 없는 회사는 결과를 `미대상`으로 두면 됩니다.
- 역량검사는 `미응시 → 결과대기 → 합격/탈락`을 구분합니다. `응시 완료`는 검사를 마쳤다는 뜻일 뿐 합격을 의미하지 않습니다.
- 서류 합격 후 역량검사 결과가 대기 중이면 현재 전형은 `AI 역검·인적성 결과 대기`입니다. 결과를 `합격`으로 저장해야 `1차 면접 준비`로 넘어갑니다.
- 역량검사가 있는데 응시하지 않은 채 마감이 지난 공고는 `AI 역검·인적성 마감 · 미응시`로 표시되며, 현황판에서 바로 `탈락`으로 정리해 종료할 수 있습니다.
- 역량검사가 `미대상`인 공고는 서류 합격 후 바로 `1차 면접 준비`로 넘어갑니다.
- 어느 단계에서든 탈락하면 해당 공고는 종료 상태가 되고, 뒤 단계는 현황판에서 `—`로 표시합니다.

### 이번 주 할 일

- 요약 카드 아래에 `⏰ 이번 주 할 일` 배너가 있습니다. 앞으로 7일 이내에 챙겨야 할 서류 마감, AI 역검·인적성 마감, 1차 면접, 2차 면접을 한 줄로 모아 빠른 순서대로 보여줍니다.
- 배너도 요약 카드와 마찬가지로 검색이나 필터 결과가 아니라 전체 공고를 기준으로 계산합니다.
- 칩을 누르면 아래 현황판이 그 기업의 공고만 보여줍니다. 챙길 일정이 하나도 없으면 배너 자체가 사라집니다.
- 탈락이나 최종합격으로 끝난 공고는 배너에 넣지 않습니다.
- `일정 내보내기 (.ics)`를 누르면 배너에 있는 일정을 캘린더 파일로 내려받아 구글 캘린더 등에 그대로 등록할 수 있습니다.

### 요약 카드와 필터

- 요약 카드는 검색이나 필터 결과가 아니라 로그인한 사용자의 전체 공고를 기준으로 계산합니다.
- `전체 공고`는 저장된 모든 공고 수입니다.
- `서류 작성`은 서류 작성 완료 수와 전체 공고 수, 완료 비율입니다.
- `서류 결과 대기`는 서류를 작성했고 서류 결과가 `대기`인 공고 수입니다.
- `서류 합격률`은 결과가 나온 서류 중 `합격 / (합격 + 탈락)`이며 결과 대기는 분모에서 제외합니다.
- `진행 중 공고`는 지원서 작성 중과 서류 결과 대기를 제외합니다. 서류에 합격했거나 이후 역량검사·면접 단계에 진입했고, 아직 탈락 또는 최종합격으로 종료되지 않은 공고만 포함합니다.
- 상태 필터의 `진행 중`도 위 요약 카드와 같은 기준을 사용합니다.
- 각 요약 카드를 누르면 해당 공고만 빠르게 필터링하고, 선택된 카드에는 각 카드의 상단 강조색과 같은 색의 테두리를 표시합니다. 같은 카드를 다시 누르면 전체 보기로 돌아가며, 카드 선택 시 검색어와 기존 드롭다운 필터는 초기화합니다.
- 서류 작성이 완료됐지만 서류 결과가 `대기`인 공고는 `현재 전형` 칸 왼쪽에 얇은 주황 표시선을 넣어 구분합니다. 노란색은 마감 임박과 상태 배지에 이미 사용하므로 행 전체 배경에는 사용하지 않습니다.
- 서류 `미작성` 체크는 경고가 아닌 중립 상태이므로 회색으로 표시하고, `작성 완료`만 초록색으로 강조합니다.
- 검색창은 기업명과 직무뿐 아니라 **JD, 우대사항, 자기소개서, 메모 본문까지** 찾습니다. 기업명·직무에는 없고 자료 본문에서만 걸린 공고는 `지원 자료` 칸의 해당 버튼에 노란 테두리를 표시해 어디서 걸렸는지 알려 줍니다.
- 탈락이나 최종합격으로 끝난 공고는 기본적으로 목록에서 접어 둡니다. 건수 문구 오른쪽의 `종료 공고 N건 보기` 버튼으로 펼치고 접을 수 있으며, 선택한 상태는 이 브라우저에 기억됩니다.
- 검색어를 입력했거나 상태 필터를 `최종 합격`·`탈락 건`으로 두었거나 요약 카드를 선택한 동안에는 접기 설정과 무관하게 종료 공고도 함께 보여 줍니다. 찾고 있는 공고가 접혀서 사라지는 일을 막기 위해서입니다. 이때 버튼은 `검색·필터 중 — 종료 공고 포함`으로 바뀝니다.
- 종료 공고를 접어도 요약 카드 다섯 개와 `이번 주 할 일` 배너의 숫자는 달라지지 않습니다. 둘 다 전체 공고 기준이기 때문입니다.

### 정렬과 마감

- 현황판은 `해야 할 마감이 남은 공고 → 진행 중 공고 → 마감을 놓친 공고 → 탈락·최종합격으로 종료된 공고` 순서로 정렬하고, 같은 날짜에서는 마감 시각이 빠른 공고를 먼저 표시합니다.
- 서류 미작성 상태로 서류 마감이 남았거나, 서류를 작성한 뒤 역량검사 마감이 남았는데 아직 미응시라면 `해야 할 일`로 판단합니다.
- 서류 작성이 끝나고 역량검사만 남았다면 행 정렬과 왼쪽 강조선은 역량검사 마감일을 기준으로 합니다. 마감 칸의 D-Day는 계속 실제 서류 마감을 보여줍니다.
- **면접일도 정렬 기준에 들어갑니다.** 결과를 기다리는 1차·2차 면접 날짜가 잡혀 있으면 그 날짜가 다음에 챙길 일정이 되어, 면접이 임박한 공고가 진행 중 공고 중 위쪽에 오고 D-3 이내면 행 왼쪽에 강조선이 켜집니다.
- 면접에는 시각 칸이 없어 그날 하루 전체를 남은 일정으로 봅니다.
- 마감 시각을 비워두면 해당 날짜의 `23:59`까지 유효한 것으로 처리합니다. 시각을 입력하면 그 시각이 지난 순간 `마감`으로 바뀝니다.
- 시각 입력은 `18:00`, `1800`, `18`, `오후 3시`, `3시30분` 등을 받아 `HH:MM`으로 정규화하며 잘못된 시각은 저장하지 않습니다.

### 특이사항 메모

- 현황판 `현재 전형` 칸의 전형 흐름 아래에 공고별 메모칸이 있습니다. 면접 복장, 담당자 연락, 과제 제출 방식처럼 기억해 둘 내용을 바로 적습니다.
- 비어 있으면 점선 테두리로, 내용이 있으면 실선으로 표시해 한눈에 구분됩니다.
- 칸을 벗어나면 내용이 달라졌을 때만 자동 저장합니다. `Cmd/Ctrl + Enter`로 즉시 저장하고 `Esc`로 되돌립니다.
- 등록·수정 패널의 `특이사항 / 비고 메모` 칸에서도 같은 내용을 쓰고 고칠 수 있습니다.
- 최대 2,000자까지 저장되며 검색과 `내 데이터 백업` JSON에도 포함됩니다.

### 저장과 동기화

- 서류 작성 여부와 역량검사 응시 완료 여부는 현황판 체크박스에서 즉시 Supabase에 저장됩니다.
- 역량검사 합격·탈락 결과는 공고 수정 패널과 현황판 `결과 입력` 양쪽에서 저장할 수 있습니다. 합격이나 탈락을 선택하면 응시 완료도 함께 적용됩니다.
- `현재 전형` 칸의 `결과 입력` 메뉴에서 합격 또는 탈락을 즉시 저장할 수 있습니다. 메뉴는 서류 → 인적성 → 1차 → 2차 → 최종 순서를 따라가며 지금 입력할 단계 하나를 가리킵니다. 면접일을 아직 잡지 않아 `미대상`인 단계도 앞 단계를 통과했다면 바로 합격·탈락을 넣을 수 있습니다. 탈락 저장은 실수를 줄이기 위해 한 번 더 확인합니다.
- 결과를 입력할 수 있는 현재 단계 칩에는 아래쪽 화살표와 버튼 효과를 표시합니다. 해당 칩을 눌러도 같은 `결과 입력` 메뉴가 열립니다. 아직 결과를 정하지 않은 단계가 입력 차례이면 점선 테두리와 함께 `미정`으로 표시하고, 그 밖의 `—` 단계는 전형 순서를 보호하기 위해 클릭할 수 없습니다.
- 역량검사 응시 완료를 다시 해제하면 기존 합격·탈락 결과는 `대기`로 되돌립니다. `미대상`은 그대로 둡니다.
- 등록·수정·삭제 및 빠른 체크가 성공하면 목록, 정렬과 요약 카드가 즉시 다시 계산되고 다른 기기에서도 같은 Google 계정으로 동기화됩니다.
- 데스크톱에서는 압축형 표로, 폭 720px 이하에서는 기업별 카드 형태로 표시합니다.
- 현황판의 첫 번째 열은 서류 마감과 역량검사 마감을 혼동하지 않도록 `서류 마감`으로 표시합니다.

## 기존 브라우저 데이터 가져오기

기존 데이터가 저장된 **같은 컴퓨터, 같은 브라우저 프로필, 같은 GitHub Pages 주소**에서 진행합니다.

1. 위 SQL에서 허용한 본인 Google 계정으로 로그인합니다.
2. 본인 계정에만 `이 브라우저에서 기존 기록을 발견했습니다` 안내가 나타납니다.
3. **기존 기록 가져오기**를 누릅니다.
4. DB 함수가 Google 로그인 제공자와 허용 이메일을 서버에서 다시 검사합니다.
5. 데이터 저장과 1회 사용 완료 처리가 하나의 DB 트랜잭션으로 성공한 뒤에만 기존 `excelJobs`가 사용자별 로컬 백업 키로 이동합니다.
6. 이후 집 컴퓨터에서 같은 Google 계정으로 로그인하면 동일한 기록이 표시됩니다.

다른 Google 계정에는 이전 버튼이 나타나지 않으며, 함수를 직접 호출해도 DB에서 거부합니다. 원격 방문자의 브라우저에는 사용자의 `localStorage`가 존재하지 않으므로 가져올 데이터 자체가 없습니다.

다만 기존 `localStorage`는 원래 암호화된 저장소가 아닙니다. 같은 컴퓨터와 같은 브라우저 프로필을 물리적으로 사용하는 사람은 개발자 도구로 기존 값을 확인할 수 있으므로, 배포 후 본인 계정으로 먼저 이전하는 것이 중요합니다.

브라우저 저장소는 사이트 주소별로 격리됩니다. 기존 데이터를 `localhost`, 로컬 파일 또는 다른 도메인에서 작성했다면 GitHub Pages 주소에서는 자동 발견할 수 없습니다.

## 데이터 안전

- 새 기록은 더 이상 `localStorage`를 원본 저장소로 사용하지 않습니다.
- 서류 작성 체크와 AI 역량검사 유형·응시 완료·합격 여부도 Supabase에 저장되어 다른 기기와 동기화됩니다.
- 다른 사용자의 행은 RLS가 읽기·수정·삭제를 거부합니다.
- 일반 사용자는 이전용 `legacy_id`, 소유자 ID와 생성 시각을 직접 쓰거나 수정할 권한이 없습니다.
- 상단의 **내 데이터 백업** 버튼으로 언제든 JSON 백업을 받을 수 있습니다.
- 사용자 입력은 `innerHTML`로 렌더링하지 않으며 채용 링크는 `http`와 `https`만 허용합니다.
- DB에도 길이, 상태값, 링크 형식과 사용자 소유권 제약조건이 적용됩니다.
- 외부 Supabase 브라우저 라이브러리는 정확한 버전으로 고정하고 SRI 무결성 검사를 적용했습니다.
